UCP CMS: modules and communication channels

The CMS is two applications. UCP Frontend (Next.js) gives editors their screens and has its own server layer, the Integration API, which is the only part that talks to the backend. UCP Backend (Apache Sling + Oak) holds content, drafts, review and publishing, renders pages and makes every permission decision. The editor's browser never calls the backend directly, except for the backend's own admin tools. The first two sections show the target state: the logical system and a separate Digital Assets service. The rest shows the modules and channels in today's code.

Logical system diagram

The target state in four parts: the CMS for editors, the content service, a separate digital assets service and the delivery layer. Inside each service the diagram marks the deployable packages: Components · templates for what a page is built from, and Business logic for the rules about what may happen to it. Every API sits in UCP Backend: the frontend only calls it. Content and files take separate paths from upload to the visitor. A page stores only the asset's id, and a file never enters the content repository.

Digital Assets: a separate service and hosting

Today a file goes through UCP Frontend's Integration API (POST /api/ucp/upload) into Oak under /content/dam/<market>/<folder>. An image up to 1.5 MB is stored as a data URL in the ucp:data property; a larger file or a PDF is stored only as metadata, without its content. The mock delivery API answers with that data URL. That is enough for a demo. In production the binaries bloat the content repository and its backups, pass through the Integration API's memory, and have no renditions and no CDN.

Proposal: digital assets as a separate system with its own API, database, object storage and CDN. Each region gets its own AWS account for it, next to the ucp-<region>-prod accounts from the hosting page. UCP Frontend and UCP Backend know only the asset's id.

Principles

  • A page stores the id (image = ast_7Q2…), never the file or a URL. The URL is built at render time, so a new crop or version changes on every page without editing them.
  • The file never passes through UCP Frontend or UCP Backend. The browser sends it straight to S3, to a signed address.
  • A new file is unavailable until it passes the scan. Only a clean file goes to the rendition queue.
  • Renditions become public only once the asset is approved. A draft preview gets short-lived signed URLs.
  • A rendition's name includes its version (hero.v3.webp), so the CDN keeps it for a year without invalidation.
  • An asset used on a published page cannot be deleted. The usage registry enforces this (channel 6).
  • Migration: a script moves the /content/dam nodes with ucp:data to S3 and the database, leaving only ids in Oak.
  • To decide: where the DAM gets an editor's roles from. Proposal: after sign-in, UCP Backend issues a short-lived signed token with the user, markets and groups.

Flow: inline text edit in the preview

The editor double-clicks a heading in the preview, changes the text and presses Enter.

Flow: review and publishing

Decisions that belong to the backend (review request, approval, send-back, publishing) go to the Management API. The intermediate review stages, comments and locks are CMS data stored beside the page in /var/ucp/pages.
